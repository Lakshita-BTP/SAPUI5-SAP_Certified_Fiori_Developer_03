# Code Execution Flow — Component.js, ListSelector.js, CarrierController.js, FlightsController.js

This document traces the exact execution order across all four files — which file, which function, and when it runs.

---

## Phase 1 — App Bootstrap

**`Component.js` → `init()`**
```javascript
init: function () {
    UIComponent.prototype.init.apply(this, arguments);   // (1) base init
    this.oListSelector = new ListSelector();               // (2) create ListSelector
    this.getRouter().initialize();                         // (3) start routing
    this.setModel(models.createDeviceModel(), "device");   // (4) set device model
}
```
- **(1)** runs first — standard `UIComponent` setup (models from `manifest.json` get instantiated here, including `i18n`, `ODataModel`, etc.).
- **(2)** `new ListSelector()` runs next → jumps into **`ListSelector.js` constructor**.

---

## Phase 2 — ListSelector constructor runs (inside step 2 above)

```javascript
constructor : function () {
    this._oWhenListHasBeenSet = new Promise(function (fnResolveListHasBeenSet) {
        this._fnResolveListHasBeenSet = fnResolveListHasBeenSet;
    }.bind(this));

    this.oWhenListLoadingIsDone = new Promise(function (fnResolve, fnReject) {
        this._oWhenListHasBeenSet
            .then(function (oList) {
                oList.getBinding("items").attachEventOnce("dataReceived", function (oData) { ... });
            });
    }.bind(this));
}
```
- The **Promise executor functions run synchronously immediately** — so `_fnResolveListHasBeenSet` gets captured right away.
- `_oWhenListHasBeenSet` is created but **stays pending** — nothing resolves it yet.
- `oWhenListLoadingIsDone`'s executor calls `.then()` on `_oWhenListHasBeenSet` — this `.then()` callback is **registered but not run yet** (it can't run until `_oWhenListHasBeenSet` resolves, which hasn't happened).
- Constructor returns. Control goes back to `Component.js`.

**Back in `Component.js`:**
- **(3)** `this.getRouter().initialize()` runs → triggers route matching based on the current URL hash. This eventually causes a view (e.g. the Carrier/Overview view) to be instantiated and its controller's `onInit` to run.
- **(4)** device model set (independent, unrelated to this flow).

---

## Phase 3 — Carrier view instantiated → `CarrierController.onInit()` runs

```javascript
onInit: function () {
    var oList = this.byId("list");
    this._oList = oList;                                    // (A) grab the list control

    this.getView().addEventDelegate({
        onBeforeFirstShow: function () {
            this.getOwnerComponent().oListSelector.setBoundMasterList(this._oList);  // (B) registered, not run yet
        }.bind(this)
    });

    this.getRouter().getRoute("Overview").attachPatternMatched(this._onListMatched, this);  // (C) registered, not run yet
    this.getRouter().attachBypassed(this.onBypassed, this);
}
```
- **(A)** runs immediately — grabs the `sap.m.List` control by ID.
- **(B)** just *registers* an event delegate callback for `onBeforeFirstShow` — it does **not** run yet. It fires when the view is about to be shown for the first time (UI5 lifecycle event).
- **(C)** registers `_onListMatched` to run whenever the `"Overview"` route pattern is matched. If the current URL already matches `"Overview"` (typical on app startup with no deep-link hash), **this fires very soon after** — essentially right after `onInit` completes.

---

## Phase 4 — Two things happen close together

### 4a. `onBeforeFirstShow` fires (view lifecycle event)
```javascript
this.getOwnerComponent().oListSelector.setBoundMasterList(this._oList);
```
→ Jumps into **`ListSelector.js` → `setBoundMasterList()`**:
```javascript
setBoundMasterList: function(oList) {
    this._oList = oList;                          // store reference
    this._fnResolveListHasBeenSet(oList);          // RESOLVE Promise #1
}
```
- This **resolves `_oWhenListHasBeenSet`** with the actual `oList` control.
- That resolution triggers the `.then()` callback registered back in the constructor (Phase 2) to now run:
  ```javascript
  oList.getBinding("items").attachEventOnce("dataReceived", function (oData) {
      // ...checks data, gets first item, resolves/rejects oWhenListLoadingIsDone
  });
  ```
  This attaches a **one-time listener** waiting for the OData binding's `dataReceived` event. Nothing resolves yet — just waiting for backend data.

### 4b. `_onListMatched` fires (route pattern matched — `CarrierController.js`)
```javascript
_onListMatched: function () {
    this.getListSelector().oWhenListLoadingIsDone.then(
        function (mParams) {
            var sObjectId = mParams.oFirstListItem.getBindingContext().getProperty("Carrid");
            this._navigateToCarrierDetails(sObjectId, true);
        }.bind(this)
    );
}
```
- This just **registers a `.then()`** on `oWhenListLoadingIsDone` — since that promise is still pending (waiting on `dataReceived`), this callback doesn't run yet either. It's now queued, waiting.

> ⚠️ **Note:** 4a must happen before or very close to 4b for this to work — specifically, the `dataReceived` listener (inside 4a's chain) must get attached **before** the actual OData response arrives, otherwise `attachEventOnce` would miss the event. In practice this works because `onBeforeFirstShow` fires as part of the view being shown, which happens very early — before the OData request round-trip to the backend completes (network latency is always slower than this synchronous setup code).

---

## Phase 5 — Backend responds (async, whenever the OData call actually returns)

The `dataReceived` handler set up in Phase 4a's `.then()` (inside `ListSelector.js`) now fires:
```javascript
function (oData) {
    if (!oData.getParameter("data")) {
        fnReject({ list: oList, error: true });
        return;
    }
    var oFirstListItem = oList.getItems()[0];
    if (oFirstListItem) {
        fnResolve({ list: oList, oFirstListItem: oFirstListItem });   // RESOLVE Promise #2
    } else {
        fnReject({ list: oList, error: false });
    }
}
```
- Data has arrived, the `oList`'s items are now populated (UI5 binding has rendered them).
- `oFirstListItem = oList.getItems()[0]` grabs the **first row** in the now-populated list.
- **`oWhenListLoadingIsDone` resolves** with `{ list, oFirstListItem }`.

---

## Phase 6 — Back in `CarrierController.js`, the queued `.then()` from Phase 4b now runs

```javascript
function (mParams) {
    var sObjectId = mParams.oFirstListItem.getBindingContext().getProperty("Carrid");
    this._navigateToCarrierDetails(sObjectId, true);
}.bind(this)
```
- Reads the `Carrid` property off the first item's binding context (e.g. `"AA"`).
- Calls:
  ```javascript
  _navigateToCarrierDetails: function (sCarrierId, bReplace) {
      this.getRouter().navTo("flights", { carrid: sCarrierId }, bReplace);
  }
  ```
  → triggers navigation to the `"flights"` route with `carrid = "AA"`.

---

## Phase 7 — Route change → `FlightsController.js` takes over

**`onInit`** (registered earlier, when the Flights view was first created — likely during initial component/router setup, since views can be lazily instantiated on first route match):
```javascript
onInit: function () {
    var oRouter = this.getRouter();
    oRouter.getRoute("flights").attachMatched(this._onObjectMatched, this);   // registers handler

    var oModel = this.getOwnerComponent().getModel();
    oModel.attachRequestSent(...);       // busy indicator wiring
    oModel.attachRequestCompleted(...);
}
```
- `attachMatched` (not `attachPatternMatched`) fires **every time** this route is matched — including the one just triggered in Phase 6.

**`_onObjectMatched` now runs:**
```javascript
_onObjectMatched: function (oEvent) {
    var oArgs = oEvent.getParameter("arguments");
    this._sCarrierId = oArgs.carrid;                              // "AA"

    var oView = this.getView();
    oView.getModel("mainView").setProperty("/layout", "TwoColumnsMidExpanded");

    oView.bindElement({
        path: "/UX_C_Carrier_TP('" + this._sCarrierId + "')",
        events: {
            change: this._onBindingChange.bind(this)
        }
    });
}
```
- Extracts `carrid` from the matched route's arguments.
- Switches the layout to two-column mode (flexible column layout pattern).
- Binds the view's element to the specific Carrier entity — this triggers a **new OData request** for `UX_C_Carrier_TP('AA')` (with its navigation properties, e.g. flights).
- Registers `_onBindingChange` to fire once the binding context resolves (or fails).

---

## Phase 8 — Binding resolves → `_onBindingChange` fires

```javascript
_onBindingChange: function () {
    var oView = this.getView();
    var oElementBinding = oView.getElementBinding();

    if (!oElementBinding.getBoundContext()) {
        this.getRouter().getTargets().display("notFound");
        this.getOwnerComponent().oListSelector.clearMasterListSelection();
        return;
    }

    var sPath = oElementBinding.getPath();
    this.getOwnerComponent().oListSelector.selectAListItem(sPath);
}
```
- If the entity **wasn't found** (bad ID, deleted record, etc.) → shows a `"notFound"` target and clears the master list's selection (→ jumps into `ListSelector.js` → `clearMasterListSelection()`, which waits on `_oWhenListHasBeenSet` — already resolved by now, so it runs immediately, calling `this._oList.removeSelections(true)`).
- If it **was found** → gets the binding's path (e.g. `/UX_C_Carrier_TP('AA')`) and calls `ListSelector.js → selectAListItem(sPath)`:
  ```javascript
  selectAListItem : function (sBindingPath) {
      this.oWhenListLoadingIsDone.then(function () {
          // finds the matching list item by binding path and visually selects it in the master list
      }.bind(this));
  }
  ```
  This highlights the corresponding row in the master (Carrier) list so the UI shows which carrier is currently selected, keeping master list and detail view in sync.

## Summary Table — Execution Order

| Step | File | Function | Trigger |
|---|---|---|---|
| 1 | Component.js | `init()` | App bootstrap |
| 2 | ListSelector.js | `constructor()` | `new ListSelector()` |
| 3 | Component.js | `getRouter().initialize()` | continues init |
| 4 | CarrierController.js | `onInit()` | View instantiated |
| 5 | CarrierController.js | `onBeforeFirstShow` delegate → calls `setBoundMasterList()` | View lifecycle event |
| 6 | ListSelector.js | `setBoundMasterList()` resolves Promise #1 | called from step 5 |
| 7 | ListSelector.js | `dataReceived` listener attached | Promise #1's `.then()` runs |
| 8 | CarrierController.js | `_onListMatched()` | `"Overview"` route matched |
| 9 | (waiting) | — | OData request in flight |
| 10 | ListSelector.js | `dataReceived` fires → resolves Promise #2 | backend responds |
| 11 | CarrierController.js | `.then()` in `_onListMatched` runs → `_navigateToCarrierDetails()` | Promise #2 resolved |
| 12 | FlightsController.js | `_onObjectMatched()` | `"flights"` route matched |
| 13 | FlightsController.js | `bindElement()` → new OData request | called from step 12 |
| 14 | FlightsController.js | `_onBindingChange()` | binding resolves |
| 15 | ListSelector.js | `selectAListItem()` | called from step 14 |

---

## Key Takeaway

The core reason for the two-promise design: **step 6 (list control exists) and step 10 (list has actual data) are two genuinely separate async events**, and `_onListMatched` (step 8) needs to wait for *both* before it can safely grab "the first carrier" — hence chaining `oWhenListLoadingIsDone` off of `_oWhenListHasBeenSet` rather than using a single promise.
